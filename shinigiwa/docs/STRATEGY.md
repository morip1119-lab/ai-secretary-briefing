# 運用戦略

## 1. 収益化の前提が 2026年9月8日に変わった

X のクリエイター収益分配（Revenue Sharing）は 2026年9月7日で終了し、翌8日から
**Original Content Rewards Program** に全面移行した。ここが今回の企画の設計に直接効いてくる。

| | 旧制度（〜2026/9/7） | 新制度（2026/9/8〜） |
| --- | --- | --- |
| 表示条件 | 直近3ヶ月で 500万インプレッション | 直近90日で **認証済みユーザーからのホームタイムライン表示 50万** （返信は除外） |
| フォロワー | 認証済み 500人以上 | 認証済み 500人以上 |
| 加入プラン | X Premium 等 | Premium / Premium+ / Premium Business |
| 報酬の対象 | 複数要素 | Premium 加入者が **投稿の50%以上を表示したユニークインプレッション** |
| 評価軸 | 高品質な投稿・会話 | **本人の視点、専門性、取材、創作** を明確に評価 |

数字だけ見ると 500万 → 50万で楽になったように見えるが、母数が「認証済みユーザーのホーム表示のみ・返信は除外」に絞られたので、実際の難易度はそれほど下がっていない。

**この企画にとって一番重要なのは最後の行**。新制度は「オリジナルコンテンツ」を評価軸に据えている。
Wikipedia の要約をそのまま流すだけのアカウントは、伸びても収益化で落とされる可能性が高い。

### だから設計にこう反映した

- 全ポストに `▼この話が刺さる理由` という**独自の解釈セクション**を入れる（`config.editorial.originalTake`）
- 画像は**自前生成のオリジナルカード**（拾い画像を使わない）
- 出典を明示して「調べて書いている」ことを可視化する
- 構成・語り口・切り口を固定フォーマット化して、アカウント固有の文体をつくる

要約botではなく「同じ視点で語り続ける書き手」に見せることが、フォロワー獲得と収益化の両方で効く。

## 2. 伸びる投稿の条件

このチャンネルの前提は一つだけ。**落差**。

```
バズ度 ≒ 昇った高さ × 落ちた深さ × 日本人にとっての知名度
```

`src/core/scorer.js` はこれをそのまま式にしてある。`fame × fallDepth` を相乗で効かせているのは、
「有名だが普通に死んだ人」も「悲惨だが誰も知らない人」も伸びないから。

### 特に強いパターン

| 型 | 例 | 効く理由 |
| --- | --- | --- |
| 富豪の孤独死 | ハワード・ヒューズ | 「金では買えないもの」という誰もが納得する結論 |
| 世界を変えた人の貧困死 | ニコラ・テスラ | 読者が「世の中は不公平だ」と共有できる |
| 頂点直前での中断 | マイケル・ジャクソン | 「あと少しだったのに」の引力 |
| 英雄への理不尽 | ジョー・ルイス | 怒りが引用リポストを生む |
| 誰も知らない最期 | 尾崎豊 | 未解決＝リプライで議論が続く |

### 弱いパターン

- 老衰・大往生（落差がない）
- 日本人がほぼ知らない人物（知名度が0だと落差も0）
- 悲惨さだけを煽っていて、成功の描写が薄いもの

### 新しい死ほど強い

読者の記憶に残っている人物ほど、落差を説明する手間がいらない。
「誰それが誰か」を説明しなければならない時点で、フックの文字数が奪われる。

そのため `scorer` は没後20年以内に最大15点を加点している。
ただし新しい題材ほど、事実誤認と遺族の反応というリスクも同じ比率で上がる。
guard は没後7年以内に警告を出すので、その警告が出た原稿だけは必ず出典に当たること。
数字を1つ間違えるだけで、そのアカウントの信用は元に戻らない。

### フックの作り方

1行目で人物名を出さない。**落差の構造だけ**を先に見せる。

- 悪い例: 「ハワード・ヒューズの晩年について」
- 良い例: 「世界一の富豪は、誰にも会わないまま暗い部屋で20年を過ごし、体重41キロで見つかった」

数字を必ず1つ以上入れる（年齢・年数・金額・体重）。抽象語だけのフックはスクロールで消える。

## 3. 投稿頻度と時間帯

初期設定は 1日3投稿（`config.posting.postsPerDay`）、最大5。枠は 07:30 / 12:15 / 19:00 / 21:30 / 22:45（JST）。

- 通勤・昼休み・帰宅後・寝る前という、長文が読まれる時間に寄せてある
- 全部が同じ分に出ると機械的に見えるので ±7分のジッターを入れている
- 1日5本を毎日は、ネタの質が確実に落ちる。**3本を維持して、勝ちパターンが見えてから増やす**

2週間ほど回したら `node src/cli.js metrics` → `stats` で時間帯別の平均インプレッションを見て、
負けている枠を `config.posting.slots` から外す。

## 4. 立ち上げの順序

### 第1段階：フォーマットを固める（〜20投稿）

- `DRY_RUN=true` のまま `generate` → `review` を繰り返し、自分が納得する文体を確定させる
- 手で直した箇所を `data/subjects.json` と `config/config.json` に反映していく
- ここで固めた型が、以降ずっと効き続ける

### 第2段階：手動投稿で反応を見る（〜100投稿）

- `export` で書き出した txt と png を自分で X に貼る
- 投稿したら `posted` で記録する（重複防止が効かなくなるので必須）
- どのカテゴリ・どの時間帯が伸びたかを手元でメモしていく
- 伸びたカテゴリの人物を `subjects.json` に厚く積む

X API を申請するのはこの段階の途中でいい。手で貼っているうちは課金もゼロで済む。

### 第3段階：自動化（100投稿以降）

- `config.posting.mode` を `api` にして X API のキーを入れる
- `config.posting.autoApprove` を `true`
- GitHub Actions か cron で `auto` を30分おきに実行
- 週1回だけ `stats` を見て、ネタの補充とスコア重みの調整をする

**在庫が最大のボトルネックになる。** 1日3投稿なら月に90本のネタが要る。
第2段階のうちに `subjects.json` を100件以上に育てておくこと。

## 5. 見るべき数字

| 指標 | 意味 | 目安 |
| --- | --- | --- |
| インプレッション | フックが機能したか | 全ポストの中央値で比較する |
| エンゲージメント率 | 本文が最後まで読まれたか | 1%を下回るならフックと中身が乖離している |
| プロフィールクリック | 「この人の他の投稿も読みたい」 | フォロワー増の先行指標。ここが一番大事 |
| 認証済みフォロワー | 収益化の申請条件 | 500人 |
| 90日ホーム表示 | 収益化の申請条件 | 50万（返信を除く） |

`metrics` は 1件 $0.005 かかる。毎時回す必要はない。**週1回のまとめ取得**で十分。

## 6. リスクの現実的な見積もり

| リスク | 起きること | 対策 |
| --- | --- | --- |
| 事実誤認 | 引用リポストで晒される。信用が一発で消える | 出典必須。`causeConfirmed` の運用を徹底 |
| 遺族・関係者からの申し立て | 投稿削除、最悪アカウント凍結 | 没後3年ルール、断定表現の禁止 |
| 「死をネタにしている」批判 | 炎上 | 煽らない。感嘆符を使わない。事実の並べ方だけで見せる |
| ネタ切れ | 質が落ちて数字が下がる | 在庫100本を切ったら補充する運用にする |
| 収益化で「非オリジナル」と判定 | 申請却下、90日待ち | 独自視点セクションとオリジナル画像を必ず入れる |

一番怖いのは炎上ではなく **「事実を間違えたまま伸びること」**。訂正が届く範囲を超えて拡散する。
`guard` は伸ばすためではなく、これを防ぐために置いてある。
